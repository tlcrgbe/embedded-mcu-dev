# 使用与交接

## 输入准备到什么程度

| 入口 | 最小可用输入 | 有益的现有材料 |
| --- | --- | --- |
| plan | 产品想实现的能力、固定工况、已确认限制 | 现有行为、资源条件、测试能力 |
| design | 已确认的功能行为与修改方向、可读取的现有工程 | 规划结果、芯片与引脚资源、调用上下文 |
| code | 已确认的行为与修改范围、相关源码 | 接口设计、任务卡、构建与验证命令 |

资料不全时允许发现缺项并集中提问；不把猜测写成产品要求。与待决项无关的明确工作仍可继续。输入不要求套固定文档模板，已有项目工件可直接使用。

## 交接看什么

plan 交给 design 的是功能边界、状态时序、依赖和验收要求；design 决定文件与接口。设计发现产品规则缺口时，返回具体问题与影响。

design 交给 code 的是源文件路径及层级、职责与状态归属、直接依赖、对外能力、必要接口和接入约定。编码发现资源或接口约束不成立时，返回设计问题，不静默改变产品行为。

任务进入实施前，将已确认设计落实到修改范围和验收要求；已有任务卡或 OpenSpec 工件承接即可。技能使用本身不授权编码以外的烧录、发布、安装或 Git 操作，也不会自动启动多代理。

## 固件层级与工作入口的区别

plan/design/code 是协作任务的分工。design 内部判断固件的底层、设备驱动、可选中间层与业务层。

例如 GPIO 的寄存器或 HAL 操作属于底层能力，灯的引脚映射、有效电平和安全初始化属于设备驱动；闪烁节奏和告警策略属于业务。驱动可以直接使用已有 HAL，不要求再补一层空转封装。目录表达实际层级，文件名表达具体能力，已有工程结构优先。

## 验证如何理解

当前组合已在维护者本机完成安装、技能发现去重、格式和 SHA256 核对，以及根代理显式读取后对规划、设计、代码评审三个控制样例的应用。Oracle 对此前组合给出可用结论；design V1.0.1 采用其措辞澄清建议。

这些结果证明该组合在该次本机检查中的可发现性和显式应用情况，不证明新聊天必然自动路由，也不证明任意工程都获得改善。新的真实任务应结合原有工程、构建、测试和必要的上板证据判断效果。

本仓库不包含内部工程源码、本机配置、评审会话、原始实验输出或个人安装备份。组件清单用于核对分发内容，历史记录放在仓库文档中。
