# MCU 功能与任务规划

面向固定硬件和已知工况，把需求转成行为明确、可设计和可验收的开发工作。以产品能力组织功能，以实际协作关系组织任务；保持高内聚、低耦合，不为假想扩展增加功能或机制。

## 恢复范围与事实

读取当前需求、相关硬件条件、已有行为和能力及项目流程，确认本次目标、固定工况与不做事项。工程事实以当前资料和相关源码为准，已有能力注明来源与复用条件；不为规划扩大到全工程调查。区分已确认需求、工程事实、建议和待决项，不把模板工程当作已实现产品。

缺失信息会改变产品行为或验收结果，且现有资料不能确定时，在相关规则定稿前优先向需求方或任务负责人集中提问一次，说明选择及影响。可附简短建议；未获确认的部分保持待决，无关部分继续规划。不自行补入产品故障恢复、重试、持久化或诊断策略。已有授权覆盖的常规选择可直接完成，遵循项目现有阶段门禁，不另建审批流程。

## 明确行为并划分功能

围绕产品能力说明触发、允许条件、输入、动作、结束条件和可观察结果，保留必要的单位、门限和时限。相关规则可集中引用，不在每项任务重复抄写。按实际责任拆分功能，列明协作与已有能力复用；不只按外设清单列功能，也不把每项功能机械变成一个文件、线程或状态机。

功能内部的规则与状态保持一致，跨功能明确谁作决定、谁提供信息、谁执行动作。这里确定产品责任，不提前决定 C 文件、接口签名、私有状态布局或消息传递机制；这些交给模块设计。

## 梳理实际状态与时序

对需求中存在的模式、持续行为及跨功能交互，明确进入和退出条件、事件先后、互斥与优先级。只记录影响产品行为的状态，不强制画状态机或为每项功能添加状态。

遇到停止、保护、超时或异步采样参与同一行为时，明确有效观察时点、数据适用范围和同时满足条件时的结果。将约束表达为外部可检查的行为，不预设队列、锁、回调、时间戳字段或调度框架。周期、门限和故障处理来自当前需求；未确定的产品取舍保持待决，不用通用默认值替代。

## 组织任务与验收

任务按可交付能力及真实依赖拆分，每项给出输入与前置条件、工作边界、输出和完成证据。职责紧密且可一起验证的工作可合并；需要独立确认或存在实质依赖的工作再拆开。不为数量完整编造任务，不把“写驱动、写业务、测试”当作充分的任务说明。

验收对应产品行为，说明场景、操作或事件顺序、期望结果与必要时间边界；重点覆盖本次正常路径和真实异常、交互冲突。涉及未确认产品建议的任务和验收，先列场景与待确认判据，不把某个建议方案写成必达结果；已确认部分照常推进。已有有效测试可复用，避免将所有理论错误排列成防御清单。区分文档核对、主机测试、编译和实机证据；未执行的验证标明后续要求，不能以编译成功替代行为验收。

## 交给设计与实施

默认交付功能与行为说明、任务及验收表、必要待决项。小任务合并表达；复杂状态和时序再补图。交接应让设计者能够确定源文件职责、状态归属和必要接口，无需重新猜测产品规则。

模块设计使用 embedded-mcu-design 或项目既有设计方法。设计确认后，再把允许修改的文件、必要接口与接入约束补入实施任务卡，交给 embedded-mcu-code 或项目编码流程。规划输出不冒充已确认的设计，未获实施授权不继续编码；纯规划请求不自动启动其他 skill 或子代理。

交付前检查需求是否有对应能力和验收，任务前置是否成立，跨功能规则是否一致，以及待决项是否被悄悄当成确定行为。沿用项目文档与治理要求，不重复生成已有工件；实验材料与迭代历史留在 skill 外。
